> **测试日期**：2026-10-22

## 一、评测背景与测试设计体系

本次评测覆盖江城燃气已启用的三大核心主题数据集，涉及系统的 12 张业务分析视图：

| 数据集 ID | 数据集编码 | 数据集名称 | 声明业务视图 | 核心管理诉求与覆盖业务域 |
|---|---|---|---|---|
| **64** | `GAS_BIZ` | 江城燃气·经营与供销差 | `v_gas_sales`, `v_gas_supply_sources`, `v_gas_supply_balance`, `v_gas_profit`, `v_gas_growth`, `v_gas_org` | 解决“规模大却不赚钱”核心痛点：销气量价倒挂、多气源采购成本、管网供销差率核定、模拟税前利润、新增通气与期末户数 |

### 1.2 题目体系与五大检验维度
为确保测试具有高度的真实性、业务深度与系统鲁棒性，本次设计的 50 道题严格遵循燃气行业管理层与审计专家的真实提问口吻，涵盖 5 大检验维度：
1. **基础单表聚合与排名（10 题）**：检验对各业务视图基本度量、维度过滤与排序的能力。
2. **加权比率与复合除法（10 题）**：重点检验是否遵守“先汇总分子分母再相除”的铁律，杜绝直接对明细行比例进行算术平均（`AVG`）的统计硬伤。
3. **时点存量与滚动平衡（10 题）**：检验期末应收、期末总户数等时点存量指标是否被错误地跨月求和，检验财务期初期末滚动平衡的勾稽能力。
4. **多表关联与历史时点回溯（10 题）**：检验管网与工单多对一关联时管网里程是否被重复膨胀，以及回看过去历史时点 T 时是否按工单发现/完成日期正确重溯状态，而非直接取当前快照状态。
5. **边界防御与防幻觉拒答（10 题）**：检验对未来/无数据月份（如 2026 年 10 月）、特殊无职能组织（如高压输配无销气业务）、超范围指标（如所得税、逐票迁徙明细、伤亡事故等）是否能准确查空或声明不支持，坚决防止大模型胡编乱造。

## 四、评测中发现的核心问题与深层技术根因

虽然本次测试 50 道题整体取得了 92% 的高符合率，且底表与视图设计的业务规范性极强，但在复杂场景、时延性能与多表关联边界上，评测发现了 **4 类典型隐患与工程瓶颈**：

### 4.1 隐患一：工单与管网多表关联时的“管网里程膨胀”风险（涉及 Q46）
- **现象描述**：隐患工单表 `v_gas_hazards` 与管网资产表 `v_gas_network` 是多对一关系（一条管段可能发生多次隐患工单）。当用户询问“重大隐患涉及多少公里管网”时，AI 模型容易直接编写：
  ```sql
  -- 错误示范：造成里程被重复计算
  SELECT SUM(n.length_km) 
  FROM v_gas_hazards h 
  LEFT JOIN v_gas_network n ON h.network_id = n.network_id 
  WHERE h.severity = '重大';
  ```
- **技术根因**：若某条 50 公里的管段上有 2 起重大隐患工单，`JOIN` 后会生成 2 行记录，`SUM(n.length_km)` 会错误输出 100 公里。
- **业务危害**：造成管网资产风险里程严重虚高，误导安全整改决策。

### 4.2 隐患二：历史时点 T 状态回溯与快照字段 `status` 的语义冲突（涉及 Q44、Q47）
- **现象描述**：在查询“回看截至 2026 年 6 月底未闭环隐患数”时，底表 `v_gas_hazards` 存在一个当前状态字段 `status`（如值为 `'已闭环'` 或 `'整改中'`）。部分未被 Golden SQL 命中的自由提问，模型倾向于直接加上 `WHERE status = '未闭环'`。
- **技术根因**：工单当前的 `status` 记录的是数据库最新快照状态（2026-09 时点）。如果在 2026 年 8 月才闭环的工单，在 6 月底时其实是“未闭环”的。直接用 `status` 筛选会导致历史未闭环工单被漏查。
- **正确口径**：必须使用双时间戳重建历史时点状态：
  ```sql
  WHERE found_date <= '2026-06-30' 
    AND (completed_date IS NULL OR completed_date > '2026-06-30')
  ```

### 4.3 隐患三：加权平均比率面临算术平均 `AVG()` 降级的潜在诱惑（涉及 Q03、Q04、Q07、Q35）
- **现象描述**：在自由长文本提问（如“看一下各分公司安检覆盖率”）时，如果用户措辞中带有“平均”二字，LLM 在生成 SQL 时极易被诱导写出 `AVG(inspected / due_inspect)` 或对网格估抄率直接 `AVG()`。
- **技术根因**：自然语言中“平均覆盖率”具有歧义。大模型的预训练语料中充斥着大量的 `AVG(rate)` 错误模式。
- **统计危害**：由于各大网格户数规模差异极大，对各网格比率求简单平均会严重偏离真实大盘比率（辛普森悖论）。

### 4.4 隐患四：单进程问数管道并发阻塞与客户端长轮询超时
- **现象描述**：在进行自动化压测或多用户并发提问时，如果直接使用阻塞式 `POST /api/ask-chat`，当并发数为 2 时即发生读超时（180s Timeout）。
- **技术根因**：
  1. 当前后端 `app.py` 启动采用默认的单进程模式；
  2. 问数流程经过 Agent 1 (意图)、Agent 2 (SQL生成)、Agent 3 (SQL审核)、Agent 4 (分析解读)，共需多次串行调用远程硅基流动 Qwen3.8-27B 大模型，单题耗时约 40~60 秒；
  3. 当多个长耗时请求并发到达时，请求在后端队列中排队，导致后续请求因客户端连接超时而断开。

## 五、系统落地优化与改进建议

> 提示：本建议完全遵循“**不需要改动系统业务源码**”的前提，聚焦于通过**知识库语义配置**、**专家提示词增强**、**Golden SQL 资产沉淀**和**运行环境参数调优**实现闭环。

### 5.1 知识库与数据字典层：强化易混淆字段定义与防膨胀约束
1. **在 `v_gas_hazards` 字典中显式注入“防里程膨胀”警示**：
   - 在数据集 66 的数据字典维护中，将 `v_gas_hazards.network_id` 的关联注释升级为：
     > *“本字段多对一关联 v_gas_network 管网资产表。严禁在关联后直接 SUM(length_km)，如需统计涉及管段总里程，必须使用 SUM(DISTINCT length_km) 或对 network_id 去重后再关联求和！”*
2. **在 `v_gas_hazards.status` 字段中增加时态说明**：
   - 注释说明：*“status 为当前最新快照状态，仅适用于查询当前未闭环工单；回看历史截止日 T 的未闭环状态时，必须忽略此字段，严格根据 found_date <= T 且 (completed_date IS NULL OR completed_date > T) 进行判定。”*

### 5.2 专家提示词层：优化 Agent 2 与 Agent 3 核心审核规则
在数据集 64/65/66 的 LLD v2 提示词模板中补充以下高约束规则：

1. **加权除法强校验规则（针对 Agent 3 SQL 审核专家）**：
   ```text
   【比率类指标强审红线】
   凡涉及均价、估抄率、供销差率、回收率、安检覆盖率、抢修及时率、GIS入库率、闭环率等比率指标：
   1. 严禁对任何预存比例列执行 AVG()！
   2. 必须重写为 SUM(分子)::numeric / NULLIF(SUM(分母), 0)；
   3. 审核专家一旦发现 SELECT AVG(...) 计算比率，必须立刻拒绝并强制退回修复。
   ```

2. **时点存量指标跨月防加总规则（针对 Agent 2 SQL 生成专家）**：
   ```text
   【时点存量指标红线】
   期末应收 (closing_yuan)、期末户数 (ending_users)、管网里程 (length_km) 为截面时点指标：
   1. 若用户询问单月，必须限定单个 month 过滤；
   2. 若用户询问历史趋势，必须按 month 逐月 GROUP BY 输出，严禁跨月累加 SUM(closing_yuan)！
   ```

### 5.3 金标资产层：将 50 题中的复杂长尾场景沉淀为 Golden SQL
当前系统具备成熟的 Golden SQL 匹配与参考机制（命中金标时执行时间从 45 秒锐减至 0.2 秒）。建议将本次实测中表现优异但逻辑较复杂的题目直接沉淀到 `generated/dataset_knowledge_bundle.json` 与 PostgreSQL 元数据表中：

- **沉淀项 1（环比计算）**：`v_gas_sales` 月度环比（使用 `LAG() OVER(PARTITION BY branch_name ORDER BY month)`）；
- **沉淀项 2（超期隐患多表关联）**：重大超期未闭环工单关联管段材质与压力等级；
- **沉淀项 3（历史重溯）**：指定历史截止日期的隐患工单闭环率与超期工单统计；
- **沉淀项 4（千公里泄漏率）**：月度安全表与管网资产表跨表关联求每千公里泄漏次数。

### 5.4 架构与运行环境调优建议（运维配置级）
1. **启用多线程/多 Worker 运行后端**：
   - 当前测试表明后端处理高并发模型请求时易排队，建议在生产启动命令或 Docker 容器内增加 `--workers 4 --threads 4`，解除单线程并发等待瓶颈。
2. **前端与 API 客户端推荐使用流式调用**：
   - 生产对接时统一调用 `/api/ask-chat/stream`，配合 Server-Sent Events (SSE) 持续抓取 trace 进度，既避免了反向代理中间件的连接空闲超时（Idle Timeout），又能为用户提供丝滑的“思考过程实时打字”交互体验。
