## 一、你的角色与任务目标

你不是来简单优化一个 SQL Prompt，也不是只讨论 Agent 概念。请以一支资深企业级 AI 数据产品研发团队的方式工作，综合承担以下角色：

1. **产品架构负责人**：梳理用户问数流程、产品模式、交互和体验。
2. **数据分析/BI 专家**：分析指标语义、数据集路由、查询口径、多轮分析与可视化。
3. **Text-to-SQL 工程专家**：检查 SQL 生成、检索、校验、执行、纠错和结果验证。
4. **多 Agent 编排专家**：设计“一个主理人 + 多个专家”的协作链路，而不是机械堆叠多个 Agent。
5. **上下文与长期记忆架构师**：解决多轮追问、跨会话恢复、任务状态保留、记忆召回和纠错生效。
6. **技术调研人员**：联网研究截至当前日期可以查证的主流智能问数/Agentic Analytics 产品及官方技术文档。
7. **质量与安全负责人**：提出能测试、能度量、可审计、可回归的验收标准。

### 最终目标

审计当前项目实际实现的问数流程，与当前主流智能问数系统做有证据的差异分析，提出一次完整的升级计划。产品仍然保留两个用户可选择的问数模式：

- **普通问数**：快速、稳定、低成本，适用于明确、简单、可标准化的问题。
- **高级问数**：由主理人 Agent 拆解复杂任务，调度多个专家，必要时多轮向用户澄清、对数据反复查询和验证，最终由主理人统一汇总交付。

两种模式不是两套互相独立、重复建设的系统，而是复用同一套数据资产、上下文、记忆、SQL 安全执行、质量验证和产物存储基础设施。高级模式在需要时调用更多专家和多步骤分析能力。

**本次先完成审计、竞品研究和升级设计，不要擅自重构或批量修改代码。** 除非我明确要求进入开发阶段，否则先交付分析报告、流程图、差距矩阵、架构建议、开发分期和验收方案。

### 项目分析的硬性要求

1. 先找到仓库入口和实际运行入口，阅读 README、目录结构、前后端路由、配置文件及相关测试。

7. 检查执行结果有没有独立验证；“SQL 执行成功”不能直接等同于“业务答案正确”。
8. 检查当前系统有没有真实的多 Agent 编排、工具权限边界、Agent 间结构化交接、调用轨迹与失败重试机制。如果只有多个 Prompt 或一次性并行调用，应明确指出这不等于成熟的专家团。
9. 对没查到的实现写“未发现/无法证实”，不要猜测。关键结论应提供文件路径、函数/类名、接口路径、表名或日志证据，尽量标出代码行号。
10. 如果仓库或运行环境不可访问，明确说明阻塞原因，给出需要用户提供的最少信息；不得把推测写成已经完成的代码审计。

## 五、设计两个问数模式：普通模式与高级专家团模式

### 模式 A：普通问数（快速与精准）

目标：回答明确、低复杂度、存在可信模板或在单个已治理数据集内可安全回答的问题。减少 Agent 数量与 token 消耗，不为简单问题启动重型专家团队。

请设计并验证以下流程是否适合本系统：

1. 接收问题，读取当前会话的结构化状态和必要历史；
2. 判断这是新任务还是对上一轮的修改/延续；
3. 提取时间、指标、维度、筛选、排序、比较和输出偏好；
4. 基于用户权限、分析主题、路由词、字段覆盖与历史有效性选择数据集；
5. 检索数据字典、指标定义、表关系、LLD、常见问题、标准题集和 Golden SQL；
6. 对可安全确定的问题直接复用经过验证的 SQL 模板；
7. 有关键歧义时仅提出必要澄清，并在用户回答后保存解析状态；
8. 生成查询计划与 SQL；
9. 静态检查、语义检查、权限/只读/资源限制检查；
10. 在受控环境执行 SQL；
11. 检查结果结构、空值、异常、聚合粒度、时间边界、重复 Join、指标分母与分子等；
12. 如失败，按错误类型有限修复/重试；达到上限后解释失败，不无限循环；
13. 返回结果表、适配的图表、必要的分析结论、统计口径、筛选条件、数据时间和可查看的 SQL/来源；
14. 更新当前任务状态，提取记忆候选，但不能自动把模型猜测写成正式业务规则。

普通模式的原则：**简单问题快速执行；可信模板优先；缺失条件才澄清；所有 SQL 仍经过安全和结果验证。**

### 模式 B：高级问数（主理人 + 多专家 + 多轮分析）

目标：解决跨数据集、复杂口径、趋势对比、异常归因、贡献分析、根因探索和多步骤决策问题。

请设计为“主理人/监督 Agent + 按需调度的专家”，而不是固定启动所有专家，也不是多个模型各自回答一遍再投票。

#### 主理人（Supervisor / Lead Analyst）职责

- 理解业务目标、恢复相关工作区和上下文；
- 对问题分类、评估复杂度与风险；
- 决定需要哪些专家、需要哪些工具、哪些任务可并行；
- 生成带依赖关系的任务计划；
- 维护唯一的权威任务状态；
- 决定何时追问用户、何时继续查询、何时要求专家复核；
- 管理预算、超时、重试、停止条件与异常回退；
- 汇总通过验证的证据、标明不确定性；
- 以用户能理解的方式交付唯一的最终结论；
- 负责将本轮可复用知识提交给记忆服务审核，而非直接任意写入长期记忆。

#### 建议的专家角色（按问题动态启用）

1. **上下文与记忆管家**：解析指代、恢复状态、检索相关记忆、识别冲突，并形成上下文包；正式业务配置仍以配置中心为准。
2. **数据资产路由专家**：选择合适数据集/表/字段，确认权限、数据时效和跨源可用性。
3. **业务语义专家**：解释指标定义、业务术语、时间口径、过滤条件、维度与粒度。
4. **查询规划专家**：把业务问题拆解为可验证的子问题、聚合和依赖步骤。
5. **SQL 工程专家**：检索并复用可信 SQL，生成/优化查询，解释 Join 与聚合逻辑。
6. **独立审查专家**：审查语义一致性、权限、安全、数据粒度、重复计数、时间边界、空值及 SQL 风险；不能只对生成 SQL 的 Agent 自我背书。
7. **数据分析专家**：执行趋势、同比/环比、贡献度、异常定位、分层比较和敏感性验证。
8. **可视化与表达专家**：选择图表、组织结论、提供可追溯的口径说明与有价值的下一步问题。

可根据需要合并部分角色，但必须说明职责边界。记忆存储、权限验证和 SQL 执行等关键能力应主要由确定性服务提供，不能只交给 Prompt。

#### 高级模式建议工作流

1. 主理人加载工作区、当前任务状态、必要对话和相关记忆；
2. 结构化解析问题，确定已知条件、未决问题、成功标准与风险等级；
3. 如果指标或范围存在会影响结论的关键歧义，先向用户提出最少必要的问题；如果能明确识别多个合理方案，给出简短选项和差异；
4. 检索权威数据资产与语义知识，形成带来源的语义约束；
5. 主理人建立可持久化任务图（DAG），定义每个子任务的输入、预期输出、依赖、验收条件和重试策略；
6. 让互不依赖的资产检索/业务定义工作并行，依赖上游结果的 SQL 任务串行推进；
7. 专家通过统一协议提交结构化结果，不能只输出自由文本意见；
8. SQL 经过确定性安全检查与审查后才允许执行；
9. 执行结果形成带来源引用的证据，分析结论必须引用结果，不能从历史记忆或模型常识凭空推出数据结论；
10. 主理人根据结果决定继续拆解/补充查询、向用户澄清、要求独立复核，或停止分析；
11. 如果要“找原因”，必须区分数据中直接观察到的相关性、贡献分析、可验证的原因线索和未经验证的因果结论；
12. 达到停止条件后，由主理人统一组织答案，提供结论、图表、证据、指标口径、SQL/执行轨迹查看入口和必要的不确定性说明；
13. 保存任务状态、查询产物、专家轨迹和记忆候选；经确认/验证后再沉淀到长期记忆或正式配置。

#### 专家交接协议

所有专家建议返回结构化数据，例如：

```json
{
  "task_id": "task_xxx",
  "agent_role": "sql_engineer",
  "status": "completed | needs_clarification | blocked | failed",
  "findings": [],
  "artifact_refs": [],
  "evidence_refs": [],
  "assumptions": [],
  "unresolved_questions": [],
  "risk_flags": [],
  "recommended_next_actions": []
}
```

实际设计时请进一步定义 Schema 和状态枚举。不要用模型自报的一个 `confidence: 0.99` 作为 SQL 正确或允许执行的唯一标准。

#### 高级模式必须有停止与降级规则

- 最多澄清几轮、最多 SQL 修复几次、最大 Agent 调用预算、最大耗时和 token 预算，都要可配置；
- 遇到权限问题不能让其他 Agent 绕过；
- 未确认的指标定义不能被默默选择；
- 专家结果矛盾时要回到证据/口径核验，不要多数投票；
- 数据不足时明确指出缺口，不要编造原因；
- 超时/服务失败时保存检查点，允许恢复；
- 复杂任务的每一步要能追溯、能重放，至少保留输入引用、配置版本、工具调用、输出与错误；
- 若发现问题其实很简单，应允许高级模式降级到普通执行路径。

## 六、上下文与记忆：作为独立底层能力设计

不要把“最近 N 条聊天消息”称作完整记忆系统。请先评估现状，再设计以下层次，并说明具体存储位置、读写时机、检索机制、版本和验收方式。

### 1. 工作记忆 / 任务状态（短期但必须可持久化）

保存当前分析正在做什么：当前指标、时间范围、维度、过滤条件、选中的数据集、口径版本、子任务状态、已执行查询、结果引用、错误、待办事项、停止条件和上下文版本。

要求：
- 结构化存储，而不是只放在对话摘要里；
- 每次用户追问按增量更新，未修改条件必须保留；
- 任务更新有版本号、时间戳和必要的变更历史；
- 支持断点恢复、重复执行保护和并发状态冲突检测；
- 记录每个过滤条件来自用户、记忆、配置还是模型推断；
- 区分已确认事实、临时假设和未解决问题。

### 2. 会话记忆

保存同一会话中的原始消息、指代关系、关键修正、确认内容和任务链接。保留近期原始对话，同时维护可更新的摘要；摘要不能取代关键原始证据。

### 3. 跨会话长期记忆

至少区分：
- 用户明确设置的分析习惯/回答偏好；
- 业务术语和口径（但正式口径需引用权威配置）；
- 历史纠错与确认记录；
- 可复用的问数/分析案例；
- 未完成工作与可恢复工作区索引；
- 失败案例和已知陷阱。

必须按用户、团队、项目、数据集或全企业划分作用范围。一个用户的个人习惯不得自动变成全组织规则。

### 4. 数据集知识 / 语义记忆

当前书架配置中的数据集描述、别名、字段字典、LLD、DDL、关联、指标、Golden SQL、标准题集、Agent 提示片段等是正式配置来源。优先读取其有效版本；模型生成的推测不能自动覆盖这些配置。

### 5. 案例记忆与验证证据

历史问答必须关联其数据集版本、指标版本、查询 SQL、执行时间、结果引用、审核状态和适用条件。历史查询可以帮助理解与构造 SQL，但历史数值不能默认当作实时数据。

### 每条长期记忆至少应有的元数据

建议评估 `memory_type`、`scope`、`content`、`source_ref`、`created_at`、`updated_at`、`valid_from`、`valid_to`、`status`、`version`、`confidence`、`access_policy`、`supersedes_memory_id`、`reviewed_by` 等字段是否需要。可以调整命名，但必须覆盖：类型、作用范围、来源、可信级别、时间有效性、版本、权限和冲突/替代关系。

### 记忆读写规则

- 当前明确用户指令优先更新当前任务状态，但不一定等于企业正式业务规则；
- 正式指标和关联以有权限的配置中心有效版本为准；
- 模型推测只能作为待验证假设；
- 用户明确纠错可以立刻修正当前任务，若要推广成长期规则/正式定义，需按权限和审核策略处理；
- 记忆冲突时，按权限、作用范围、来源可靠性、生效时间和版本处理，无法确定则澄清；
- 记忆失效或被撤销的条目不应继续作为有效事实返回；保留必要审计记录；
- 用户应能查看、纠正、撤销与清理其有权管理的记忆；
- 记忆检索不能越权，也不能把敏感数据不必要地注入不相关 Agent 的上下文。

### Context Packet（统一上下文包）

请设计一个由上下文服务生成的标准上下文包，至少包括：

- `conversation_id`、`workspace_id`、`task_id`、`context_version`；
- 当前问题和意图；
- 已确认的指标、时间、维度、筛选、排序与比较条件；
- 每个条件的来源和确认状态；
- 数据集、语义模型、Golden SQL 等资产引用及版本；
- 相关记忆引用和有效期；
- 已完成步骤、查询产物引用、待办任务与未决问题；
- 权限范围、执行限制、预算和停止条件；
- 当前任务对话摘要与必要的近期原文引用。

各 Agent 共享同一权威任务状态，但按职责拿到最小必要上下文。不要为每个 Agent 单独生成互相冲突的“真相”。

### 记忆检索机制

不能只有向量相似度。请比较和设计结构化过滤、关键词检索、语义检索、来源/版本/时间过滤、权限过滤及结果重排序的组合。明确如何控制记忆数量与上下文窗口；压缩时优先保留当前约束、权威口径、未决问题和执行状态，不应优先删掉这些关键信息。

## 七、必须设计的 SQL 与结果质量闸门

请逐项评估当前实现并给出目标架构：

1. 数据集/表/字段白名单和权限验证；
2. 只读 SQL 约束，禁止非授权 DDL/DML/多语句等风险操作；
3. SQL AST/方言解析或其他确定性静态检查；
4. 表关联、Join 粒度、重复计数、指标分子分母与聚合层级检查；
5. 时间边界、时区、自然月/滚动周期和同比/环比规则；
6. 敏感字段、行列权限和参数化；
7. 查询超时、扫描量/返回行数限制、成本预算与取消机制；
8. 执行错误分类，限次修复，不进行无限自我循环；
9. 结果结构验证、空结果/异常值/重复行/聚合合理性检测；
10. 关键指标的参考 SQL、可信查询或基准结果校验；
11. 业务口径无法确认时的阻断与澄清；
12. 每个答案中的指标口径、数据源、时间范围、筛选条件和 SQL/逻辑可追溯入口。

强调：模型审查不能替代程序化 SQL 安全校验和数据库权限；SQL 执行成功也不能证明业务语义正确；多个 Agent 意见一致也不能代替结果证据。

## 八、把“持续学习”设计成可控反馈闭环

请检查并规划以下闭环：

1. 收集用户反馈：正确、错误、部分正确、口径不符、图表不合适、需要补充条件；
2. 将反馈关联到本次 `task_id`、上下文版本、使用的配置版本、SQL、结果和专家轨迹；
3. 将反馈分类：意图识别错误、数据集路由错误、语义口径错误、SQL 错误、执行问题、结果解释错误、记忆错误等；
4. 生成候选修复：新增别名、修订业务定义、补充 Golden SQL、修改检索/Prompt/规则，或增加测试用例；
5. 对候选知识进行冲突检查、权限检查、人工审核或自动验证；
6. 只有通过审核的正式知识才能进入可信配置；
7. 将修复案例加入回归测试集，防止下一版本复发；
8. 跟踪修复后的命中率、SQL 正确性、澄清率、记忆准确性、成本和延迟变化。

不要默认把每次对话都永久存成长期记忆，也不要未经验证就让模型自我修改正式数据集配置。

## 九、升级计划必须具体到工程可执行

完成当前系统审计和竞品研究后，请不要只写原则。必须输出一份有依赖、有验收标准、有优先级的实施计划。

### 交付物 A：当前系统问数流程审计

- 当前实际执行链路图；
- 上下文与记忆现状图；
- 关键代码、接口、表、配置、Prompt 的证据索引；
- 已实现/部分实现/未实现/无法确认清单；
- 具体缺陷、复现方式、影响范围及严重程度。

### 交付物 B：市场对标研究

- 产品能力比较表；
- 每项关键能力的官方来源与发布日期/更新日期；
- DataBuddy 身份确认结果及资料不足之处；
- 最值得借鉴的 5–10 项机制；
- 明确哪些机制适合本系统，哪些成本过高、不应直接复制。

### 交付物 C：目标方案

- 普通问数完整时序图；
- 高级专家团完整时序图；
- Supervisor 与各专家的职责边界、触发条件和交付协议；
- 统一任务状态、Context Packet、记忆模型和检索流程；
- SQL/结果质量闸门；
- 前端交互建议：用户模式切换、澄清问题、专家执行状态、来源/SQL查看、分析工作区恢复、记忆管理；
- 失败、超时、冲突、权限和降级的处理策略。

### 交付物 D：差距矩阵

每个问题都写清：

| 能力点 | 当前实现证据 | 目标能力 | 差距/根因 | 用户影响 | 优先级 | 依赖项 | 改造方案 | 验收测试 |
|---|---|---|---|---|---|---|---|---|

不要把所有能力都标为 P0；请按业务价值、质量/安全风险、实施成本和依赖进行排序，并解释优先级理由。

### 交付物 E：分期升级路线图

至少拆为：

- **P0：必须先补齐的基础能力**（如真实流程可观测性、任务状态、权限/SQL安全、关键条件继承等，以实际审计为准）；
- **P1：普通问数质量提升**（语义路由、可信 SQL、澄清、结果验证、错误分类修复）；
- **P2：高级多 Agent 协作**（主理人、任务 DAG、按需调度、专家协议、独立验证、执行检查点）；
- **P3：长期记忆与反馈闭环完善**（跨会话恢复、版本/冲突/失效管理、案例学习和自动回归）；
- **P4：进阶分析体验**（异常归因、跨数据集、多轮钻取、图表调整和可复现报告）。

阶段可根据代码依赖调整，不必机械照搬以上顺序。每阶段需写：目标、改动模块、关键数据结构/API、依赖、风险、预计工作量区间、验收标准及回滚策略。

### 交付物 F：测试集与量化指标

必须设计真实场景测试，不只测单轮问题：

- 单轮基础取数；
- 自然语言别名/口语提问；
- 指标口径歧义；
- 多轮追加、修改、删除过滤条件；
- 跨会话继续昨天的分析；
- 用户纠错后本轮状态立即更新；
- 权威配置升级后旧记忆失效；
- 跨数据集连接；
- 复杂异常分析需要多次查询；
- SQL 生成失败和数据库超时恢复；
- Agent 输出互相矛盾；
- 权限隔离与敏感字段；
- 上下文过长时的重要信息保留。

建议评估指标包括：

- 问题路由准确率、语义/指标解析准确率；
- SQL 执行成功率、SQL 语义正确率和结果一致性；
- 澄清问题命中率与不必要澄清率；
- 多轮条件继承正确率；
- 记忆召回精确率/召回率、错误记忆写入率、过期记忆误用率；
- 跨会话状态恢复成功率；
- 高级模式任务完成率、无证据结论率、专家冲突解决率；
- 平均时延、P95 时延、模型调用次数、token 成本、SQL 执行成本；
- 权限/安全测试通过率。

先基于当前项目建立基线，再设定目标阈值。不要随意承诺 99% 准确率；对无法自动验证的指标明确评估方法和人工标注要求。

## 十、设计决策必须回答的问题

请在最终报告中逐项明确回答：

14. 第一阶段最少需要改哪些文件/接口/表，怎样做到小步可回滚？

## 十一、执行纪律与输出要求

- 先审计和研究，再提出升级方案；本阶段不要擅自改代码或部署。
- 不要只输出长篇概念。所有建议必须映射到当前代码、配置、接口、数据结构或清晰的新模块。
- 不要假设增加 Agent 就一定提升质量。需要通过消融测试证明各 Agent 的价值，并比较普通路径与高级路径的成本/质量。
- 不要把原始聊天历史无限塞进上下文。应采用结构化任务状态、相关记忆召回、最近对话和可追溯产物引用组合。
- 不要把记忆系统当成“自动学习全部用户话语”。必须有作用范围、证据来源、可信状态、版本和删除/失效规则。
- 不要让模型自我审查成为唯一安全机制；SQL 安全、权限、只读和执行资源管控必须有确定性保护。
- 不要对未经验证的数据做因果归因；区分观察事实、统计贡献、原因假设和经验证的因果结论。
- 对所有竞品结论附官方来源。资料不足则明确标注，不得捏造产品内部机制。
- 输出要让产品经理、后端、前端、数据工程师和 AI 工程师都能据此开工。
- 报告开头先给一页执行摘要和最关键的 5 个问题；中间给证据与细节；结尾给推荐架构、分期计划和下一步最小改造集。
- 每个高优先级改造必须附上可执行的验收测试。
